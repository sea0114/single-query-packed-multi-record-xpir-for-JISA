# Measurement and statistical definitions

## Current core evaluation

The current definitions and commands are in [core_rebuild/README.md](../experiments/core_rebuild/README.md). The new runner gives each method one shared, sealed preprocessed database and fresh query processes. Included timing starts before preparation dispatch; excluded timing starts after the shared database is ready. Both end after all requested record bytes and completion signals are collected. Whole-group CPU includes the coordinator and timed native children; preprocessing is recorded directly. A common four-CPU guest affinity pool and the accepted sampled 8 GiB monitor policy apply to every method. These are guest resource controls, not host exclusivity or a hard memory limit.

The formal matrix has 28 conditions and ten sessions. A paired block consists of one complete retrieval task per method on the same synthetic database and ordered target tuple. A latency contrast first takes each session's median of six paired `baseline/P` ratios, then the median across ten sessions. Absolute costs use within-session medians followed by the median across sessions. Joint whole-session resampling uses 10,000 common index draws across contrasts and metrics, with pointwise linear-percentile intervals. Every expected task, including warmups, must be complete and validated before a condition receives an estimate. The recorded time variation, weaker comparisons and actual buffer counts remain in the full-precision outputs. The primary study includes same-width and independently tuned repeated baselines; the capacity study uses predeclared fixed layouts. The immutable `R_matched` field denotes same-width repeated retrieval. None of the historical samples below is pooled with this run.

## Tasks, encoding and timing

Each task retrieves the same ordered tuple of distinct record indices. Packed retrieval executes one multi-record task; repeated retrieval executes alpha independent single-record retrieval processes concurrently. A raw `worker` is one retrieval process; `parent` is the coordinating process that launches them and collects results. Within a comparison, both methods use the same database, public layout, ring degree, modulus and paired parameters. Every process has a fresh client key and private database preprocessing; pair membership does not mean the packed and repeated tasks run simultaneously.

The backend has n=4096, a 122-bit ciphertext modulus formed from two RNS primes, and recursion/aggregation factors of one. Coefficient width is w=alpha*rho_0, so t=B^alpha. Measurements used a Ryzen 7 3700X with Ubuntu under WSL2; host scheduling, frequency and turbo remained host managed.

Task latency uses timed TaskTotal endpoints recorded with `CLOCK_MONOTONIC_RAW`: one packed timed span, or latest single-record timed end minus earliest timed start. Dispatch skew within those endpoints is included; process wall times are not summed. Both scopes time fresh client configuration/key generation, query generation, reply generation, extraction and associated buffer copies. **Preprocessing included in timing** also times server configuration, database encoding and native import. **Preprocessing excluded from timing** stages the same process-private database before the endpoint, while retaining fresh key generation inside timing. Raw `COLD`/`ONLINE` fields map to those scopes; they are not persistent-service, amortized or network latency. Process startup, test-data generation, logging, teardown and validation after the endpoint are excluded. No transport is measured.

Native encoding zero-extends each rho_0-bit segment into its declared w-bit field, then pads the sequence to L*n fields before import. A partial final segment and remaining polynomial fields are separately zero padded. Import must match the specified polynomial coefficients; extraction uses the same layout and trims to ell bits. Changing w requires rebuilding preprocessing. `native_xpir/m1_adapter.hpp` implements segment adaptation, radix weights, field reading and decoding; `native_xpir/s4_n/support.hpp` supplies the checked full-block API path. The primary implementation extracts record-used fields; the two-to-four-record path extracts complete blocks through checked wrappers. These are implementation differences, not different formal encodings. [building.md](building.md#native-support-and-functional-evidence) gives width/weight restrictions.

## Designs and resource policies

| Experiment | Conditions and measured pairs | CPU assignment | Memory policy |
|---|---|---|---|
| Primary two-record | 96 conditions; alpha=2, N=256/1024/4096/16384, ell=256/512/1024/2048 bits, rho_0=8/12/16, both scopes; 2,160 measured pairs | Serial packed arithmetic allowed two logical CPUs; two repeated processes pinned separately; coordinator has the same allowance | Packed address-space cap 16 GiB; each repeated process 8 GiB; aggregate sampled RSS cap 16 GiB |
| Two to four records | 24 conditions; alpha=2/3/4, N=1024/4096, ell=512/2048 bits, rho_0=8, w=8*alpha, both scopes; 240 measured pairs | Packed on one logical CPU; alpha repeated processes on distinct CPUs from a four-CPU set that also bounds the coordinator | Each process address-space cap 8 GiB; aggregate sampled virtual-memory cap 16 GiB |
| Configuration sensitivity | Eight conditions at N=1024, ell=512, alpha=2, rho_0=8; 240 measured pairs | Crosses record-field/full-block implementation and the two resource policies above | Resource treatments include CPU and memory changes together |
| Record length | Five lengths in two scopes at N=1024, alpha=4, rho_0=8, w=32; 300 measured pairs | Full-block implementation and four-CPU-coordinator policy | Same policy as the two-to-four-record study |

CPU assignment restricts allowed logical CPUs; the two-CPU allowance does not parallelize packed arithmetic or establish physical host isolation. Address space is a process's virtual address range; virtual memory and resident set size (RSS, memory currently resident in RAM) are different quantities. The limits cannot all be described as common "16 GiB memory". Changing alpha changes both width and repeated-process count, so the multiplicity study is not fixed-total-resource scaling.

Primary uses three warmup pairs and 30/30/20/10 measured pairs per condition as N increases. Two-to-four-record uses three warmup pairs and ten measured pairs. Each sensitivity/record-length condition has three successive sessions, each with three warmups and ten measured pairs, balanced five/five method order and interleaved conditions. Different conditions do not execute concurrently. Pilot data are excluded. The last two studies contain 540 measured and 162 warmup pairs, all completed; those 702 pairs are not primary or multiplicity samples.

Sensitivity compares configurations, not isolated operations. The public test-data generation rule is common, but rebuilding retains extraction/wrapper differences; extra record-field coefficient validation is outside task timing. Sensitivity medians range from 1.123 to 1.236. Implementation ordering changes with resource policy and scope, and session ranges overlap within each fixed policy/scope. No unique cause of the historical two-record effect difference has been established.

Record lengths are 4096/8192/12288/16384/65536 bits. First four have L=1; the last has J=8192 and L=2. Historical coefficient-slot quantity alpha*J/n and record-block boundary J=n are distinct. No coefficient-position alternative was implemented or timed, and one L=2 workload does not establish performance for arbitrary block counts.

## Estimators and uncertainty

For a complete paired trial k, form `R_k=T_repeated,k/T_packed,k`; latency estimator is `median_k(R_k)`, not a quotient of separate method medians. Absolute-time medians describe each method separately. CPU work ratios use separate medians, as specified below.

Primary and two-to-four-record intervals are pointwise 95% percentile intervals from 10,000 paired-bootstrap resamples. Seeds reset per condition: primary `2026092401`, two-to-four-record `2026092501`. Archived implementation uses `random.Random(...).choices`, medians and type-7 percentile endpoints; exact replay environment was Python 3.12.3. Warmups are excluded. Schedule balance and deterministic replay do not establish sample independence, coverage under temporal dependence or simultaneous coverage. Historical batches are not independent sessions.

Sensitivity and record-length brackets are the minimum and maximum of three successive session medians: descriptive ranges, not confidence intervals or independent-day replications. JSON/CSV retain full precision. Display rounding does not determine exclusion: an endpoint displayed as 1.000 may lie below or above one. Only three of eight multiplicity alpha=2 intervals exclude one; all eight do at each of alpha=3 and alpha=4. Experiments remain separate and are not pooled.

Failed, incomplete and unstarted attempts remain recorded. There are no retries, outlier deletion, replacement or imputation. Missing/failed warmups withhold that sensitivity/capacity condition-session summary. Stopping rules concern resource, correctness and integrity failures, not effect size; sample counts are not extended after viewing ratios. All reported measured pairs completed.

## CPU, memory monitoring and buffers

CPU work sums user-plus-system CPU-time deltas over TaskTotal for retrieval processes only. Coordinator CPU is separate; its whole-runner interval is not added. In the two-to-four-record study, ratios of separate repeated/packed CPU medians are 1.972–2.052, 3.033–3.149 and 4.085–4.295 for alpha=2,3,4. These describe reduced repeated computation, not alpha-fold latency improvements. Summed phase durations are process work spans; envelopes may overlap or contain gaps and do not partition the critical path.

Packed lifetime RSS includes staged state. Repeated RSS sums process lifetime peaks, which need not occur simultaneously; the sum is an upper bound rather than a synchronized task peak. Coordinator RSS is separate. Native pre-exit RSS and final `wait4` lifetime RSS may differ. A largest monitoring sample is an observed sampled peak, not an instantaneous maximum.

Individual primary/two-to-four-record monitoring time series were not retained. Historical `resource_samples.jsonl` is an endpoint/lifetime ledger with null sample timestamps. Transient virtual-memory/swap behavior cannot be recovered from summaries. Sensitivity/capacity retains 99,751 observations in 1,404 monitoring files, actual timestamps and nominal 10 ms sampling. This is not exact cadence, and neither zero monitoring overhead nor physical host isolation is established. Existing traces are retained rather than reconstructed.

One ciphertext buffer occupies `2 components * 2 RNS residue arrays * 4096 coefficients * 8 bytes = 131072 bytes` (128 KiB). Two arrays correspond to backend moduli. Packed query/reply buffers contain N/L ciphertexts; same-layout repeated tasks contain alpha*N/alpha*L. Raw byte-aligned database is N*ell/8 bytes, counted once. These exclude framing, metadata, keys and transport; they are neither serialized wire sizes nor total process memory. The flat query exceeds raw database size at reported lengths, including a factor of 16 at ell=65536. No raw-download timing advantage follows.
